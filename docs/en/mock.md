# Mock Listener

The `mock` listener responds directly to requests without calling an upstream
service. Each request selects a named scenario with `X-Mock-Scenario`.
Scenarios can be configured at startup or changed at runtime through the admin
API.

## Static responses

```yaml
listeners:
  - name: test-api
    type: mock
    address: ":8081"
    mock:
      scenarios:
        user-found:
          match:
            method: GET
            path: /users/42
            headers:
              X-Tenant: demo
          response:
            status: 200
            headers:
              Content-Type: application/json
            body: '{"id":42,"name":"Ada"}'
        unavailable:
          response:
            status: 503
            headers:
              Retry-After: "30"
            body: service unavailable
```

The `match.method`, `match.path`, and `match.headers` criteria are optional;
all configured criteria must match. The default static status is `200`, and
the body and headers are empty (a text `Content-Type` is added by default).

```bash
curl -H 'X-Mock-Scenario: user-found' \
  -H 'X-Tenant: demo' \
  http://127.0.0.1:8081/users/42
```

Without `X-Mock-Scenario`, the listener responds with `400`. An unknown
scenario or a scenario whose criteria do not match responds with `404`.

`X-Mock-Scenario` also accepts `MatchWildcard` wildcards (`*`, `?`, and
`[abc]` character classes). An exact scenario name takes precedence. A pattern
matching multiple scenarios is rejected with `400` instead of choosing one
arbitrarily.

## Path parameters

`match.path` accepts named parameters in the `:name` form, each occupying one
complete segment. For example, `/users/:id` matches `/users/42`. Once the
scenario matches, Yaegi code can read the value with Go's standard API:

```go
id := response.Request.PathValue("id")
```

Parameters are set after listener middlewares run, so they are available in
`response.code`, but not in those middlewares.

## Computed response with Yaegi

For more complex responses, set `response.code` instead of `status`, `headers`,
and `body`. The code is evaluated with Yaegi and must define
`dynamic.Middleware` with the signature `func(*http.Response) error`. The
incoming request is available through `response.Request`; the code generates
the status, headers, and body by modifying `response`.

```yaml
listeners:
  - name: test-api
    type: mock
    address: ":8081"
    mock:
      scenarios:
        greet:
          match:
            method: GET
            path: /greet
          response:
            code: |
              package dynamic

              import (
                "fmt"
                "io"
                "net/http"
                "strings"
              )

              func Middleware(response *http.Response) error {
                name := response.Request.URL.Query().Get("name")
                if name == "" {
                  name = "world"
                }
                response.StatusCode = http.StatusOK
                response.Header.Set("Content-Type", "text/plain; charset=utf-8")
                response.Body = io.NopCloser(strings.NewReader(
                  fmt.Sprintf("Hello, %s!", name),
                ))
                return nil
              }
```

The code is compiled at startup; a compilation error prevents the server from
starting. Scenarios added through the admin API are compiled before they are
registered. `response.code` cannot be combined with `response.status`,
`response.headers`, or `response.body`.

Dynamic code runs with the privileges of the GORP process. Only load
configuration from trusted sources. Invalid statuses or headers, or an error
while executing the code, produce a `500` response.

`response.Body` must be an `io.ReadCloser`, not a `[]byte`. To use the result
of `json.Marshal`, wrap the bytes, for example with
`io.NopCloser(bytes.NewReader(body))`. A panic in Yaegi code is also recovered
and returned as `500`.

## Per-request overrides

The following headers can change a scenario response for a single request,
including a response generated by code:

- `X-Mock-Status` overrides the status (accepted values: `200` through `599`);
- `X-Mock-Body` overrides the body;
- `X-Mock-Response-Header-<Name>` replaces or adds a response header.

Overrides are applied after dynamic code. HTTP framing headers such as
`Content-Length` and `Transfer-Encoding` cannot be set this way.

```bash
curl -H 'X-Mock-Scenario: unavailable' \
  -H 'X-Mock-Status: 429' \
  -H 'X-Mock-Body: try again' \
  -H 'X-Mock-Response-Header-Retry-After: 5' \
  http://127.0.0.1:8081/any-path
```

`X-Mock-Body` is suitable for small bodies; use a configured or computed
scenario for larger responses.

## Admin API

The admin API can list, create/replace, and delete scenarios. It is available
only for configured mock listeners and inherits admin middlewares, so protect
this endpoint.

```bash
curl -X PUT http://127.0.0.1:9090/mocks/test-api/scenarios/user-found \
  -H 'Content-Type: application/json' \
  -d '{"match":{"method":"GET","path":"/users/42"},"response":{"status":200,"body":"found"}}'
curl http://127.0.0.1:9090/mocks/test-api/scenarios
curl -X DELETE http://127.0.0.1:9090/mocks/test-api/scenarios/user-found
```

Scenarios created through the API are kept in memory and do not survive a
restart. The `PUT` JSON body uses the same `match` and `response` fields as the
configuration, including `response.code`.

## TLS and middleware

The listener accepts standard TLS configuration (certificate, key, TLS
options, and mTLS) and HTTP listener middlewares. Request middlewares run
before scenario selection; response middlewares remain route-only.

```yaml
listeners:
  - name: secure-mock
    type: mock
    address: ":8443"
    tls:
      cert_file: /etc/gorp/tls/server.crt
      key_file: /etc/gorp/tls/server.key
    middlewares:
      - name: add_request_headers
        config:
          headers:
            X-Mock-Environment: test
    mock:
      scenarios:
        healthy:
          match:
            path: /health
            headers:
              X-Mock-Environment: test
          response:
            body: OK
```

The mock listener does not support backends or TCP routes.
